### 3.1 Google — отозвать ключ сервисного аккаунта (ГЛАВНОЕ)

Пострадавший ключ восстановлен из `.env` и `sync/credentials.json` — это **один и тот же ключ**:

| Поле | Значение |
|---|---|
| Project ID | `project-0356c8d8-e895-493d-927` |
| Сервисный аккаунт | `duty-sheets-api@project-0356c8d8-e895-493d-927.iam.gserviceaccount.com` |
| Client ID | `106079307463377960054` |
| **Private key ID (удалить именно этот ключ)** | `a35827140ad11cf5d8de5a4f271c0c76c3986f77` |

Порядок действий:

1. **Удалить ключ**: IAM & Admin → Service Accounts → `duty-sheets-api@…` → Keys →
   удалить ключ с ID `a35827140ad11cf5d8de5a4f271c0c76c3986f77`.
   Прямая ссылка:
   `https://console.cloud.google.com/iam-admin/serviceaccounts/details/106079307463377960054/keys?project=project-0356c8d8-e895-493d-927`
   **Не тяните.** Удаление ключа мгновенно запрещает выпуск новых токенов, но
   access-токен, который атакующий мог успеть выменять по ключу, живёт до 1 часа.
   Каждый час промедления — новый шанс.
2. Нужен «стоп-кран» — **отключить сам сервисный аккаунт** (Disable) на время ротации.
3. **Оценить ущерб.** Логи могут быть недоступны, поэтому смотрим по фактам:
   - Roles: какие IAM-роли привязаны к `duty-sheets-api@…`. Если ролей нет, ущерб
     ограничен объектами Drive, расшаренными на этот аккаунт.
   - **Таблица**: File → Version history — видны правки и их время.
   - Cloud Logging → Logs Explorer, фильтр
     `protoPayload.authenticationInfo.principalEmail="duty-sheets-api@project-0356c8d8-e895-493d-927.iam.gserviceaccount.com"`.
     **Важно:** Data Access audit logs по умолчанию выключены, и задним числом их не
     включить — скорее всего истории там просто нет. Опирайтесь на «Таблица» и на
     проверку расшаренных файлов.
   - Проверить, не расшарена ли таблица «по ссылке» (Anyone with the link): тогда
     данные утекли бы и без ключа.
4. **Проверить радиус доступа.** В `sync/sync.py` запрашивался
   `https://www.googleapis.com/auth/drive` — это доступ ко **всему**, что расшарено на
   сервисный аккаунт, а не только к вашей таблице. Просмотрите расшаренные объекты и
   уберите лишнее; в коде scope уже сужен до `auth/spreadsheets`.
5. **Перевыпустить ключ** (после удаления старого) и обновить его **во всех местах**:
   - `GOOGLE_SHEETS_CREDENTIALS` в `~/duty/.env` (права `600`) — основной источник,
     в коде переменная приоритетнее файла;
   - GitHub Secret `GOOGLE_SHEETS_CREDENTIALS` — CI перезаписывает `.env` при деплое,
     без этого следующий push в main вернёт старый ключ;
   - локальные `.env` и `sync/credentials.json` (файл теперь только фолбэк для
     локального запуска, в контейнер он не монтируется);
   - затем `docker compose up -d --force-recreate sync`.
6. Убедиться, что старый ключ нигде не остался:
   `grep -rl "a35827140ad11cf5d8de5a4f271c0c76c3986f77" ~/` (и в снапшотах/бэкапах).
7. На будущее: не возвращать `auth/drive` в scope, не передавать ключ в контейнер `api`,
   не дублировать ключ одновременно в env и в файле, включить бюджетные алерты,
   при желании — срок жизни ключей через org policy.

`sync_metadata`, `sync_history`.

Выводы:

1. **PIN-хеши (bcrypt)** утекли. Это не плейнтекст, но при PIN из 4 цифр
   (10 000 вариантов) офлайн-перебор тривиален, даже с bcrypt. Значит,
   PIN-ы нужно **сменить принудительно** по всем пользователям.
2. **ФИО сотрудников + графики дежурств** — персональные данные. Если применим

   идентификация — `name` + `pin`, роль проверяется параметрами `admin_name`/`admin_pin`

4. **PIN-ы в логах nginx.** Так как PIN передаётся в query-строке, `access.log`
   содержит их в открытом виде. Логи нужно сохранить как доказательства, но
   обращаться с ними как с секретом и не выкладывать в репозиторий/тикеты.
5. Домен `mediahlg.ru` — если скомпрометированы ключи TLS, отслеживайте абузы/спам
   с домена и проверьте DNS-записи на изменения.

## 9. Follow-up по коду: убрать `admin_pin` из query-параметров

Сейчас админские эндпоинты принимают `admin_name`/`admin_pin` в URL
(`api/app/routers/users.py`, `sync_history.py`, и фронтенд формирует такие ссылки
в `frontend/index.html`). Из-за этого PIN-ы попадают в логи nginx, в историю браузера
и в `Referer`.

Скетч решения (сделать отдельным PR после мержа текущей работы, чтобы не конфликтовать):

```python
# api/app/security.py
from fastapi import Header, HTTPException, Depends
from sqlalchemy.orm import Session
from .database import get_db
from . import crud

def require_admin(
    x_admin_name: str = Header(..., alias="X-Admin-Name"),
    x_admin_pin: str = Header(..., alias="X-Admin-Pin"),
    db: Session = Depends(get_db),
) -> str:
    if not crud.verify_pin(db, x_admin_name, x_admin_pin) or not crud.is_admin(db, x_admin_name):
        raise HTTPException(status_code=403, detail="Admin access required")
    return x_admin_name
```

Далее в роутерах `admin: str = Depends(require_admin)` вместо двух query-параметров,
а на фронтенде — заголовки `X-Admin-Name` / `X-Admin-Pin` вместо query-строки.
Следующий шаг после этого — заменить `name`+`pin` на токены сессии.
