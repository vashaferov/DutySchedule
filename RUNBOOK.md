# RUNBOOK: деплой, база, бэкапы

Практическая инструкция на случай «что-то сломалось». Что и почему сделано —
в `SECURITY_INCIDENT.md` (безопасность) и в комментариях к `docker-compose.yml`.

## Где что лежит на сервере

| Что | Путь |
|---|---|
| Код | `~/duty` (клонируется/обновляется CI) |
| Конфиг и секреты | `~/duty/.env` (chmod 600, перезаписывается на каждом деплое) |
| Данные Postgres | docker-том `duty_pgdata` |
| Бэкапы БД | `~/duty-backups` (ежедневно, храним 14 дней) |
| Лог бэкапов | `~/duty-backups/backup.log` |
| Логи nginx | `~/duty/logs/nginx` (на хосте, чтобы переживали пересоздание контейнера) |
| Лог ротации логов | `~/duty-backups/rotate-logs.log` |
| Контейнеры | `duty_postgres`, `duty_api`, `duty_sync`, `duty_nginx` |

Живость контейнеров: `docker compose ps` — в колонке STATUS видно
`healthy`/`unhealthy` (healthcheck-и есть у `postgres`, `api`, `sync`, `nginx`).

Логи приложений: `docker compose logs --tail=100 api` (так же `sync`, `postgres`).
Размер у них ограничен (3 файла по 10 МБ), но **при пересоздании контейнера они
исчезают**, а пересоздание — это каждый деплой. Поэтому логи nginx, нужные для
разбора происшествий, пишутся ещё и на хост — см. «Логи nginx».

## Деплой

Деплой запускается автоматически на push в `main` (`.github/workflows/deploy.yml`):
тесты → SSH на сервер → `git pull` → пересборка `.env` → **бэкап БД** → `docker
compose up -d --force-recreate --build` → ожидание `/api/health` → проверка, что
nginx отвечает по HTTPS → проверка, что в базе есть пользователи → cron для
бэкапов и ротации логов → чистка старых образов.

Бэкап перед деплоем — это дамп на момент выкатки, а не вчерашний из cron. Если
новая версия испортит данные, откат кода их не вернёт, а этот дамп вернёт.

Перед этим в CI: pytest, проверки фронтенда, синтаксис и тесты скриптов,
`nginx -t` для конфига nginx и разбор `docker-compose.yml`. Ошибка в любом из
двух последних файлов роняет сайт целиком, поэтому деплой ждёт их проверки.

Если деплой упал:

1. `cd ~/duty && docker compose ps` — все ли контейнеры `Up`.
2. `docker compose logs --tail=100 api` — чаще всего это ошибка подключения к БД
   или отсутствующая переменная в `.env`.
3. `docker compose logs --tail=100 nginx` — если 502/504 снаружи.
4. Деплой не «откатывается» сам: актуальное состояние — текущий `main`.
5. Если лог оборвался на `Бэкап БД перед деплоем` — деплой остановился **до**
   пересоздания контейнеров, сайт продолжает работать на старой версии. Причина
   в `~/duty-backups/backup.log`; исправьте бэкап и запустите деплой снова.
   Именно так 22.10.2026 выяснилось, что бэкапы не сохранялись вообще.

## Откат

Точка возврата — тег `rollback-ГГГГММДД`, поставленный на версию, которая в этот
момент работала. Тег запушен в GitHub и не меняется. Например,
`rollback-2026-10-22` — версия перед выкаткой ограничения попыток входа,
healthcheck-ов и логов nginx.

Перед следующей рискованной выкаткой поставьте свою точку (это не запускает
деплой, тег можно пушить в любой момент):

```bash
git tag -a rollback-ГГГГММДД -m "рабочая версия перед <что меняем>"
git push origin rollback-ГГГГММДД
```

**1. Понять, что именно сломалось.** Код и конфиги откатываются тегом ниже.
Испорченные данные (пропали даты, репертуар, пользователи) откат кода не
вернёт — это «Восстановление из бэкапа».

**2. Откатить сервер (1–2 минуты, без CI и GitHub):**

```bash
ssh <сервер>
bash ~/duty/scripts/rollback.sh rollback-2026-10-22
```

Скрипт делает `git reset --hard` на тег, пересобирает контейнеры и ждёт
`/api/health`. Данные в Postgres не трогает: том `duty_pgdata` остаётся, таблицы
переживают откат. Новая таблица, созданная сломанной версией (например
`login_attempts`), просто перестаёт использоваться — старой версии она не мешает.
`.env` и `logs/` не в git, поэтому тоже остаются на месте.

Список доступных точек отката: `bash ~/duty/scripts/rollback.sh` без аргументов.

**3. Закрепить откат в git.** Пока `main` содержит плохой коммит, следующий push
снова выкатит его. Поэтому отмена должна быть коммитом:

```bash
git revert --no-edit <плохой-коммит>   # локально, в main
git push origin main
```

Деплой соберёт и выкатит отменяющую версию; `main` и сервер снова совпадут.
Серверный `reset --hard` при следующем `git pull` это переживёт: отменяющий
коммит содержит ровно старое состояние.

**4. Если сломан сам GitHub Actions** (workflow не запускается, тесты падают на
инфраструктуре) — серверный откат из п.2 работает без CI и остаётся в силе, пока
workflow не починен. Для этого он и сделан отдельным скриптом.

**5. Проверить после отката:** `curl -s https://mediahlg.ru/api/health`,
`cd ~/duty && docker compose ps` (все `healthy`), вход в приложение.

**Чего откат не делает:**

- не восстанавливает данные — только `scripts/restore-db.sh`;
- не отменяет внешние эффекты: синхронизацию с Google Sheets, отправленные
  сообщения, утёкшие секреты. Секреты **меняют**, а не откатывают
  (см. `SECURITY_INCIDENT.md`);
- не удаляет `.env` и `logs/` (они не в git).

### Что проверять после деплоя

- `curl -s https://mediahlg.ru/api/health` → `{"status":"ok"}`.
- `docker compose ps` → у `postgres`, `api`, `sync`, `nginx` статус `healthy`.
- В «Истории синхронизации» время — в вашем часовом поясе, а не в UTC.
- Удалённая дата уходит из листов «График» и «Репертуар» после следующей синхронизации
  (её можно дёрнуть кнопкой в UI, не дожидаясь автосинка).

## Схема базы данных

Миграций (Alembic) в проекте нет. Схему создаёт сам API при старте:
`Base.metadata.create_all` в `api/app/main.py`. Операция идемпотентная и **не
трогает существующие таблицы** — новые таблицы появятся, но новые колонки в
старых таблицах `create_all` НЕ добавит. Если в будущем понадобится новая
колонка, её придётся добавить вручную:

```bash
docker exec -it duty_postgres psql -U duty -d duty -c "ALTER TABLE ... ADD COLUMN ..."
```

Тот же `create_all` есть в `sync/http_server.py`, чтобы sync не падал, если
стартовал раньше API.

## Пустая база (авария: потерян том pgdata)

API поднимется и создаст таблицы, но в базе не будет пользователей, и войти в
приложение будет некому. Деплой об этом предупредит, но НЕ будет ничего заливать
автоматически.

Два пути:

**1. Восстановление из бэкапа (правильный путь, если бэкап есть).**
См. раздел «Восстановление из бэкапа».

**2. Импорт из Google Sheets (если бэкапа нет).** Это работает, только если
таблица актуальна: данные, которые успели появиться в приложении после
последней синхронизации, будут потеряны.

```bash
cd ~/duty
# ADMIN_NAMES — кому выдать роль админа, если в листе «Пользователи» нет колонки «Роль»
docker compose --profile tools run --rm -e ADMIN_NAMES='Имя,ДругоеИмя' migrate
```

По умолчанию скрипт только доливает недостающее и не стирает данные. Чтобы
перезалить с нуля:

```bash
docker compose --profile tools run --rm -e MIGRATE_RESET=1 migrate
```

Сервис `migrate` вынесен в профиль `tools` именно поэтому: обычный
`docker compose up -d` его НЕ запускает, и стирания данных на каждом деплое
не происходит.

## Бэкапы

Ежедневный бэкап в 03:15 (время сервера) ставится автоматически при деплое:
cron вызывает `~/duty/scripts/backup-db.sh`, дампы складываются в
`~/duty-backups`, хранятся 14 дней. Каждый дамп проверяется на читаемость
(`gzip -t` + `pg_restore --list`) до того, как старый будет признан годным —
битый бэкап хуже отсутствующего.

> **22.10.2026:** выяснилось, что бэкапы не сохранялись вовсе. `pg_dump -F c`
> отдаёт формат `PGDMP`, а скрипт проверял его через `gzip -t` и всегда падал;
> ошибка была видна только в `backup.log`, а деплой её не замечал. Теперь дамп
> сжимается на лету (`pg_dump ... | gzip`), а `tests/scripts/backup-db.test.sh`
> проверяет это в CI до деплоя. Если `ls -lh ~/duty-backups` не показывает
> ни одного `duty-*.dump.gz` — бэкапов нет, несмотря на cron.

Проверить, что бэкапы идут:

```bash
ls -lh ~/duty-backups
tail -20 ~/duty-backups/backup.log
crontab -l | grep backup-db
```

Сделать бэкап вручную:

```bash
~/duty/scripts/backup-db.sh
```

**Бэкап лежит на том же диске, что и база.** Пока нет копии наружу, смерть
диска уносит и базу, и бэкапы. Настроить копирование можно переменной
`BACKUP_REMOTE` (например, через rclone):

```cron
15 3 * * * ENV_FILE=~/duty/.env BACKUP_REMOTE='rclone copy "$DUMP" remote:duty-backups' ~/duty/scripts/backup-db.sh >> ~/duty-backups/backup.log 2>&1
```

### Проверить, что бэкап действительно восстанавливается

Это единственный способ узнать, что бэкап рабочий. Разворачиваем в одноразовую
базу, смотрим, что данные на месте, удаляем:

```bash
cd ~/duty
DUMP=$(ls -t ~/duty-backups/duty-*.dump.gz | head -1)
echo "Проверяю $DUMP"

docker run --rm -d --name duty_restore_test \
  -e POSTGRES_PASSWORD=test -e POSTGRES_USER=duty -e POSTGRES_DB=duty postgres:15
sleep 8

gzip -dc "$DUMP" | docker exec -i duty_restore_test \
  pg_restore -U duty -d duty --no-owner
docker exec duty_restore_test psql -U duty -d duty -tAc \
  "select (select count(*) from users) as users, (select count(*) from duty_dates) as dates;"

docker rm -f duty_restore_test
```

### Восстановление из бэкапа

**Восстановление затирает текущую базу.** Всё, что появилось после снятия
дампа, будет потеряно — сначала снимаем свежий бэкап текущего состояния, чтобы
было куда вернуться:

```bash
cd ~/duty
~/duty/scripts/backup-db.sh            # сохранить текущее состояние
~/duty/scripts/restore-db.sh ~/duty-backups/duty-ГГГГММДД-ЧЧММСС.dump.gz
```

Скрипт проверяет дамп, останавливает `api` и `sync` (чтобы в базу никто не
писал), разворачивает дамп с `--clean --if-exists`, поднимает сервисы обратно.
После восстановления стоит вручную дёрнуть синхронизацию в UI и убедиться, что
имена дежурных и репертуар на месте.

## Логи nginx

Логи лежат в `~/duty/logs/nginx` — это каталог на хосте, смонтированный в
контейнер (`./logs/nginx:/var/log/nginx`). Так сделано намеренно: внутри образа
эти файлы — симлинки на stdout/stderr, и при пересоздании контейнера они исчезают
вместе с ним. Именно поэтому access-логов за 17.10.2026 уже не было, когда их
разбирали.

Ротацию делает `~/duty/scripts/rotate-nginx-logs.sh` по cron — ежедневно, в то же
время, что и бэкап: файл копируется в `access.log.ГГГГММДД-ЧЧММСС.gz`, исходный
усекается (nginx продолжает писать в него, перезапуск не нужен), архивы старше
14 дней удаляются.

```bash
ls -lh ~/duty/logs/nginx                                      # что есть
zcat ~/duty/logs/nginx/access.log.*.gz | grep '17/Oct/2026'    # нужный день
tail -50 ~/duty/logs/nginx/error.log
crontab -l | grep nginx-logs                                  # задача ротации на месте
tail -20 ~/duty-backups/rotate-logs.log                       # как прошла ротация
```

Если ищете следы перебора PIN, они тут же: `POST /api/auth/login` с ответом
401 (неверный PIN) или 429 (сработал лимит). Сам PIN в логах не появляется: он
уходит телом запроса, а не в URL (см. `SECURITY_INCIDENT.md`, §9).

## Мониторинг: как узнать, что что-то сломалось

Три уровня, независимые друг от друга:

1. **healthcheck контейнеров** — `docker compose ps` показывает `healthy`/
   `unhealthy` для `postgres`, `api`, `sync`, `nginx`. Если сервис упал, его
   перезапустит `restart: unless-stopped`, а статус это покажет.
2. **деплой** — ждёт ответа `/api/health` и падает, если API не поднялся за 60 с.
3. **внешний аптайм-чек** — GitHub Actions (`.github/workflows/uptime.yml`)
   каждые 15 минут проверяет снаружи `https://mediahlg.ru/`, `/api/health` и срок
   сертификата. При падении GitHub пишет письмо владельцу репозитория. Запустить
   проверку вручную: Actions → Uptime check → Run workflow.

Чего в этом наборе нет: проверки входа и работы с данными (для этого нужен PIN)
и SMS/Telegram-уведомлений. Если нужны они — подойдут бесплатные внешние сервисы
(UptimeRobot и подобные), подписка на них оформляется вручную.

Через 60 дней без коммитов GitHub отключает расписание аптайм-чека — если
репозиторий надолго замер, проверку надо включить заново.

## «Слишком много попыток входа» (429)

Так отвечает ограничитель перебора PIN (`api/app/ratelimit.py`): больше 5 неудач
на пользователя или 60 неудач с одного IP за 15 минут — вход отклоняется с
текстом, где сказано примерное время ожидания.

Ждать: лимит снимается сам, вмешательство админа не нужно. Успешный вход сбрасывает
счётчик этого пользователя (но не чужие — иначе один опечатавшийся блокировал бы
весь офис с общего адреса).

Пороги заданы в `docker-compose.yml` (`LOGIN_MAX_FAILURES_PER_USER`,
`LOGIN_MAX_FAILURES_PER_IP`, `LOGIN_WINDOW_MINUTES`). **Правка `~/duty/.env`
вручную не сохранится:** деплой перезаписывает файл. Чтобы поменять пороги
насовсем, добавьте значения в секреты GitHub и строку в heredoc `.env` в
`deploy.yml`.

## Быстрая справка

```bash
cd ~/duty

docker compose ps                     # состояние контейнеров
docker compose logs --tail=100 api    # логи API
docker compose restart api            # перезапуск API
docker compose up -d --force-recreate api sync   # пересоздать API и sync

bash scripts/rollback.sh              # список точек отката
bash scripts/rollback.sh rollback-2026-10-22     # откатить код на точку возврата

docker exec -it duty_postgres psql -U duty -d duty     # psql в базу
docker exec duty_postgres pg_dump -U duty -d duty -F c > /tmp/manual.dump   # дамп вручную
```

Порт Postgres (5433) проброшен только на `127.0.0.1` сервера — снаружи база
недоступна, подключаться нужно через SSH-туннель:

```bash
ssh -L 5433:127.0.0.1:5433 <user>@mediahlg.ru
```
